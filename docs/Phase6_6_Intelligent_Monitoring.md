# Phase 6.6 — Alerts and intelligent monitoring

Monitoring owns separate rules and alerts and never writes source inventory, shipments or Phase 5 finances. Independent permissions `analytics:monitoring:view` and `analytics:monitoring:manage` protect `/api/v1/analytics/monitoring` routes. Rules require an exact client and facility; authenticated identity authorizes each scope independently of tenant filter bypass. Scope and metric remain immutable; name, comparison, threshold, severity and enabled state are configurable.

Rules support five explicit evidence metrics: available quantity per stock row, damaged quantity percentage where total quantity is positive, active shipment transit hours, current SLA overdue hours with contractual policy and a live consistently scoped shipment, and indicative projected freight billed-versus-quoted variance percentage with positive quoted baseline and observed billed/quoted counts. Freight cohort summaries are indicative anomalies rather than invoice audit results. SLA and freight history are bounded to 366 days; missing sources/denominators produce no observation.

Comparisons are strict GreaterThan/LessThan with configurable nonnegative thresholds. Stable rule/evidence identities deduplicate repeated evaluations. Acknowledged breaches retain acknowledgement; recovery resolves an alert when its observed value no longer breaches. Explicit manual resolution requires notes. Rules are level-triggered: evaluation reopens manually resolved alerts if the source still breaches. Missing/deleted evidence preserves last-known state and LastObservedAtUtc, which consumers must use to identify stale evidence; absence is not interpreted as recovery. No delivery, claim or invoice lifecycle changes follow from an advisory.

GET rules lists up to 1,000 ordered scoped rules. GET alerts accepts page 1..1,000,000 and size 1..200 and orders by lifecycle, descending severity, observation time and ID. POST rules creates, PUT rules/{id} configures, PUT rules/{id}/enabled controls evaluation, POST rules/{id}/evaluate evaluates, POST alerts/{id}/acknowledge and /resolve manage advisory state.

With `Monitoring:Enabled=true`, a hosted worker evaluates enabled rules every five minutes, paging persisted rules in batches of 100. Source queries carry the persisted rule's exact client/facility constraints. Individual rule failures are logged, failed tracked state is cleared, and subsequent exact scopes continue; cancellation still stops the cycle. Failed rules retry on the next interval. No outbound notification integration is enabled.

The additive migration creates monitoring tables with unique rule/evidence keys, a composite rule/client/facility foreign key, indexes and PostgreSQL xmin alert concurrency. Rule mutations and evaluation serialize through bounded process semaphore stripes and PostgreSQL transaction advisory locks. The transaction uses the configured EF execution strategy; retries clear and reload state. Migration and live PostgreSQL concurrency verification are recorded below after completion.
